# Story 5.5-8: Fix Photo Upload `Base64 of undefined` Crash

Status: review

## Story

As a user creating an eBay listing on the mobile app,
I want the photo from my valuation to attach to the listing automatically,
so that my listing carries through to eBay with the photo I already took, instead of forcing me to re-add it manually.

## Background

During real-device testing of Story 5.5-2 the listing screen logged this warning **four times** for two different listings:

```
WARN  Photo upload failed: [TypeError: Cannot read property 'Base64' of undefined]
```

The user-visible symptom is the "Photo upload failed — listing will copy without a photo URL" banner on the Create Listing screen (visible in 5.5-2 device screenshots 5 and 7). The listing form still works — it just degrades to a copy-without-photo flow.

**Root cause:** `apps/mobile/lib/storage.ts` imports `import * as FileSystem from 'expo-file-system'` and accesses `FileSystem.EncodingType.Base64`. In Expo SDK 54 (the project's current SDK — `package.json` shows `expo-file-system: ~19.0.21`) the module split into a **new synchronous/class API** under the bare specifier and a **legacy callback API** under `expo-file-system/legacy`. The `EncodingType` enum only lives in the legacy subpath. The other call site, `apps/mobile/app/(tabs)/index.tsx:3`, already imports from `'expo-file-system/legacy'` — that is why camera capture works and photo upload doesn't.

The existing unit test `apps/mobile/__tests__/storage.test.ts:7-10` masked the crash: it hand-mocked `expo-file-system` with `EncodingType: { Base64: 'base64' }`, so the test passed against a fake module shape that does not match what the real bundle resolves at runtime.

## Acceptance Criteria

1. The listing screen no longer logs `TypeError: Cannot read property 'Base64' of undefined` when a valuation with an image is opened.
2. A successful upload returns a public Supabase Storage URL (existing behavior preserved).
3. `apps/mobile/__tests__/storage.test.ts` mocks the same module path that `lib/storage.ts` imports from, so the test can never again pass while the production code is broken.

## Dev Notes

### Why not the new sync API?

Expo's new sync `File` API (`new File(uri).base64()`) is the long-term replacement, but:
- It is sync-only, so it would block the JS thread on large photos.
- The async `readAsStringAsync` path in `expo-file-system/legacy` is already battle-tested and matches what `tabs/index.tsx` uses elsewhere in the app.

The minimal fix uses the legacy import. Migrating both call sites to the new API is a separate, larger refactor that should land alongside the next SDK bump, not as part of a hotfix.

### Why the test masked the bug

The test mocked the module by name; jest does not validate that the mocked shape matches the real module's exports. The fake shape `{ readAsStringAsync, EncodingType: { Base64: 'base64' } }` matched what `storage.ts` *expected*, so the test passed even though the real `expo-file-system` (sans `/legacy`) does not export `EncodingType` at all.

The fix flips the mock target to the same path the production code imports from. That way the next time someone copies an import without thinking, the test breaks at the first run.
