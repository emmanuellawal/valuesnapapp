# Story 5.5.3: Wire and Polish Settings Screen

Status: done

## Story

As a ValueSnap user,
I want my Theme, Notifications, and Currency preferences to be interactive and persist across app restarts,
so that the Settings screen reflects my actual choices and I can trust it rather than dismiss it as non-functional.

## Acceptance Criteria

1. Tapping Theme cycles through `System → Light → Dark → System`; the displayed value updates immediately and persists across app restarts
2. Tapping Notifications toggles `Off ↔ On`; the displayed value updates immediately and persists
3. Tapping Currency cycles through `USD → GBP → EUR → CAD → AUD → USD`; the displayed value updates immediately and persists
4. Settings screen content is not obscured by the native status bar on iOS and Android (verified by device or simulator)
5. No visible scrollbar appears within the settings screen on web/mobile-web; scrolling still works on native
6. The `preferences.ts` module exposes a generic `getPreference<T>` / `setPreference<T>` pair AND typed convenience wrappers (`getTheme / saveTheme`, `getNotifications / saveNotifications`, `getCurrency / saveCurrency`) backed by `AsyncStorage`, each with appropriate default values
7. All three preference rows re-read their persisted values each time the Settings screen is focused (app-switch and in-app navigation)
8. Unit tests in `__tests__/preferences.test.ts` cover: read/write/default for each preference key, graceful recovery from `AsyncStorage` failure (no crash)
9. Existing tests pass — no regressions in other screens caused by `ScreenContainer` layout change
10. Story includes a `## Code Review` section before being marked `done`

## Dev Notes

### Critical: @react-native-async-storage/async-storage is already installed

Do NOT run `npm install @react-native-async-storage/async-storage`. It is already in `apps/mobile/package.json` dependencies (confirmed). Installing it again would update the lockfile unnecessarily.

### preferences.ts module design

Follow the exact pattern established in `lib/localHistory.ts`:
- Import: `import AsyncStorage from '@react-native-async-storage/async-storage';`
- Key prefix: `valuesnap:` (e.g., `valuesnap:theme`, `valuesnap:notifications`, `valuesnap:currency`)
- Error handling: `try/catch` on every AsyncStorage call, always fall back gracefully — never propagate an AsyncStorage error to the UI
- No React, no hooks — pure async functions, importable from anywhere

**Naming convention — `save*` not `set*`:** The React `useState` setters inside `settings.tsx` will be named `setTheme`, `setNotifications`, `setCurrency`. Naming the AsyncStorage helpers `setTheme` etc. would shadow the state setters at the import site and cause silent bugs (persist call becomes a state call). Use the `save*` prefix for persistence helpers.

Typed module signature:

```ts
type ThemePreference = 'system' | 'light' | 'dark';
type NotificationsPreference = 'on' | 'off';
type CurrencyPreference = 'USD' | 'GBP' | 'EUR' | 'CAD' | 'AUD';

export async function getPreference<T>(key: string, defaultValue: T): Promise<T>
export async function setPreference<T>(key: string, value: T): Promise<void>
// Typed convenience wrappers (get = read, save = persist):
export async function getTheme(): Promise<ThemePreference>
export async function saveTheme(value: ThemePreference): Promise<void>
export async function getNotifications(): Promise<NotificationsPreference>
export async function saveNotifications(value: NotificationsPreference): Promise<void>
export async function getCurrency(): Promise<CurrencyPreference>
export async function saveCurrency(value: CurrencyPreference): Promise<void>
```

### Theme preference is store-only — NOT wired to ThemeProvider in this story

`app/_layout.tsx` line 141 drives app appearance with `useColorScheme()` from React Native, which reads the OS setting only. Making the stored Theme preference actually *change app appearance* would require:

1. Swapping `useColorScheme()` for a new hook that merges the stored `ThemePreference` with OS scheme (`'system'` = passthrough, `'light'`/`'dark'` = override)
2. Designing and verifying a Swiss dark palette (currently the `SwissTheme` is light-only; there is no corresponding dark Swiss theme)
3. Threading the effective scheme through every component that reads colours directly (e.g. `SwissTheme` vs. `DarkTheme` in `_layout.tsx`)

**This story is explicitly scoped to persist-and-display only.** The row shows the user's selection and it survives app restart, but the app's visual theme continues to follow the OS until a follow-up story implements override wiring. Do **not** touch `_layout.tsx`, `useColorScheme.ts`, or `SwissTheme`. A follow-up story for override wiring belongs in Epic 7 (Accessibility & Polish) alongside a Swiss dark palette decision — it is out of scope here.

Notifications and Currency are also store-only by nature (no real push registration in this story; currency is stored for future Epic 6/7 use). All three preferences behave identically: persist and display.

### Currency picker: inline cycling, NOT a BottomSheet

The epic plan offers "bottom sheet or inline picker". No BottomSheet library is installed in the project (`package.json` checked). Adding one for three currencies is over-engineered. Use **inline cycling** (same UX pattern as Theme): tapping cycles `USD → GBP → EUR → CAD → AUD → USD`. This is consistent, zero new dependencies, and reversible. If a real picker is ever wanted, Story 6 or later can add a library at that point.

### settings.tsx wire-up: useFocusEffect pattern

`useFocusEffect` from `expo-router` (not from `@react-navigation/core`) is the correct import — already in the repo from `app/(tabs)/history.tsx` line 3. `useCallback` comes from React. Both must be imported. Use the wrapper pattern established in `history.tsx` and the `isMounted` flag naming already used there (keep naming consistent across screens):

```ts
import React, { useCallback, useState } from 'react';
import { useFocusEffect } from 'expo-router';
import { getTheme, saveTheme, getNotifications, saveNotifications, getCurrency, saveCurrency } from '@/lib/preferences';

const [theme, setTheme] = useState<ThemePreference>('system');
const [notifications, setNotifications] = useState<NotificationsPreference>('off');
const [currency, setCurrency] = useState<CurrencyPreference>('USD');

useFocusEffect(
  useCallback(() => {
    let isMounted = true;
    async function loadPreferences() {
      const [t, n, c] = await Promise.all([getTheme(), getNotifications(), getCurrency()]);
      if (isMounted) { setTheme(t); setNotifications(n); setCurrency(c); }
    }
    loadPreferences();
    return () => { isMounted = false; };
  }, [])
);
```

The `isMounted` flag prevents state updates after unmount (same safety pattern as `history.tsx`, same variable name for cross-screen consistency).

**Optimistic update trade-off (accepted):** The `onPress` handlers update local state *before* calling `saveTheme / saveNotifications / saveCurrency`, and the save helpers swallow errors internally. In the rare case an AsyncStorage write fails (disk full, platform API broken), the UI shows the new value until the next screen focus, at which point `useFocusEffect` re-reads the persisted (old) value and the row flips back. This is **intentional** — the alternative (await-and-rollback) would require re-throwing errors from the persist helpers, breaking the AC8 contract ("setPreference does not throw on AsyncStorage failure") and adding complexity for a failure mode that is extremely rare on mobile. Do NOT change the persist helpers to re-throw.

### SettingsRow onPress enables SwissPressable automatically

`SettingsRow` in `settings.tsx` already implements: "if `onPress` is undefined → render `Box`; if `onPress` is provided → render `SwissPressable`". Adding `onPress` to the three preference rows immediately upgrades them to tappable `SwissPressable` components without any structural changes needed.

**Display value formatting rule:** uppercase the first letter of theme and notifications values (`system → System`, `light → Light`, `dark → Dark`, `off → Off`, `on → On`). Currency codes render as-is (`USD`, `GBP`, `EUR`, `CAD`, `AUD`). A one-liner helper or inline `value.charAt(0).toUpperCase() + value.slice(1)` is fine — no i18n scaffolding needed for this story.

### Safe-area fix scopes to ScreenContainer only

`ScreenContainer` is in `components/primitives/screen-container.tsx`. The tabs layout uses `headerShown: false` for all screens, which means all tab content starts from the very top of the screen (underneath the native status bar). The current `pt-16` (64px) is a rough approximation that works on most devices but can mis-align on notched or tall-bar devices.

Fix: replace the hardcoded NativeWind top-padding class with a computed style:

```tsx
import { useSafeAreaInsets } from 'react-native-safe-area-context';
// inside the component:
const insets = useSafeAreaInsets();
// on the Box:
style={{ paddingTop: Math.max(insets.top, 64) }}
// remove 'pt-16' from the NativeWind className
```

`react-native-safe-area-context` is already in `package.json`. The `SafeAreaProvider` wraps the app via the Expo Router stack — `useSafeAreaInsets` will work immediately.

This change affects **all 11 screens** that wrap in `ScreenContainer`:

| Group | Files |
|---|---|
| Tabs | `app/(tabs)/index.tsx`, `app/(tabs)/history.tsx`, `app/(tabs)/settings.tsx` |
| Auth | `app/auth/sign-in.tsx`, `app/auth/register.tsx`, `app/auth/forgot-password.tsx`, `app/auth/update-password.tsx` |
| Account | `app/account/delete-confirm.tsx` |
| Flow | `app/appraisal.tsx`, `app/listing/[id].tsx`, `app/demo-loading.tsx` |

**Why it is safe across all 11:** every one of these screens is under a `Stack.Screen` that sets `headerShown: false` (verified in `app/_layout.tsx` lines 146–149 for tab/auth/account groups, and per-screen `Stack.Screen` calls for `appraisal.tsx`, `listing/[id].tsx`, `demo-loading.tsx`). Because there is no native header above any of them, `Math.max(insets.top, 64)` never double-pads — it always replaces a fixed approximation with the correct device inset. The safe-area bug exists on all of them, and the fix is non-breaking for all of them.

### Scrollbar fix

`ScrollView` with no `showsVerticalScrollIndicator` defaults to `true` (scrollbar visible on web). Add the prop:

```tsx
<ScrollView
  className="flex-1 bg-paper"
  contentContainerStyle={{ flexGrow: 1 }}
  showsVerticalScrollIndicator={false}  // add this
  {...scrollProps}
>
```

This is a display-only change — scrolling itself is unaffected.

### Testing: AsyncStorage mock is wired via moduleNameMapper

The mock is supplied by an explicit `jest.moduleNameMapper` entry in `apps/mobile/package.json`:

```json
"@react-native-async-storage/async-storage": "<rootDir>/node_modules/@react-native-async-storage/async-storage/jest/async-storage-mock.js"
```

**Do NOT add a manual `jest.mock('@react-native-async-storage/async-storage')` call in the test file** — it would conflict with the moduleNameMapper mock and cause unpredictable behaviour. Just import `AsyncStorage` from the real package; the mapper swaps in the mock transparently.

Test setup pattern (copy from `__tests__/localHistory.test.ts` lines 6, 12–15):

```ts
import AsyncStorage from '@react-native-async-storage/async-storage';
import { getPreference, setPreference, getTheme, saveTheme } from '@/lib/preferences';

beforeEach(async () => {
  await AsyncStorage.clear();
});
```

To simulate AsyncStorage failure, use: `jest.spyOn(AsyncStorage, 'getItem').mockRejectedValueOnce(new Error('disk full'))`.
