# Story 5.5-9: Replace `Linking.openURL` Fallback Links with `WebBrowser.openBrowserAsync`

Status: done

## Story

As a user who hits a LOW-confidence valuation or a generic error,
I want to tap "Verify on eBay" / "Search eBay manually" and have the link open reliably,
so that I can complete my workflow without seeing a red error log and without the link silently doing nothing.

## Background

During 5.5-2 device validation the Metro log surfaced this **uncaught** promise rejection:

```
ERROR  [Error: Uncaught (in promise, id: 0) Error: Unable to open URL:
        https://www.ebay.com/sch/i.html?_nkw=headphones&LH_Complete=1&LH_Sold=1]
```

Two compounding issues:

1. **Wrong API for native external URLs in Expo Go.** `apps/mobile/components/molecules/error-state.tsx:104-113` and `apps/mobile/components/molecules/confidence-warning.tsx:34-43` use `Linking.canOpenURL` + `Linking.openURL`. On iOS Expo Go this path is fragile for arbitrary `https://` URLs — `canOpenURL` interacts with iOS's `LSApplicationQueriesSchemes` and Expo Go has known edge cases where `openURL` rejects even after `canOpenURL` resolves true. The codebase already has the right tool in scope: `expo-web-browser` is in `package.json` and `apps/mobile/components/ExternalLink.tsx:20` already uses `WebBrowser.openBrowserAsync` — that path opens a SafariViewController (iOS) or Chrome Custom Tab (Android) and does not depend on `canOpenURL` whitelisting.

2. **Uncaught promise rejection.** Both call sites use `onPress={() => openUrl(url)}`. The `openUrl` function is async; the press handler discards the promise. When `Linking.openURL` rejects, no `.catch` exists, so React Native's unhandled-rejection tracker logs the error. The user sees a tappable link that quietly does nothing AND a red Metro log entry. Both are bad signals.

## Acceptance Criteria

1. `ErrorState.fallbackLink` and `ConfidenceWarning` "Verify on eBay" link no longer surface `Uncaught (in promise, id: 0) Error: Unable to open URL` in the Metro log.
2. On native (iOS/Android), the link opens an in-app browser (Safari View Controller / Chrome Custom Tab) via `WebBrowser.openBrowserAsync`. On web, behavior is unchanged (`window.open`).
3. If `WebBrowser.openBrowserAsync` rejects (rare — e.g. user closes the system sheet immediately), the rejection is caught and logged via `console.warn`, never as an unhandled rejection.
4. New unit tests for `ErrorState` `fallbackLink` onPress and `ConfidenceWarning` "Verify on eBay" onPress confirm the WebBrowser path is invoked.

## Dev Notes

### Why not extract a shared `openUrl` helper?

It's tempting to drop a shared helper into `apps/mobile/lib/openUrl.ts`. Two reasons not to in this story:

- The two call sites have only-just-different platform branches (`window.open` vs `openBrowserAsync`) and identical catch behavior. A shared helper saves 8 lines and adds one import to two files. Net wash.
- This story is a hotfix. Adding a new module means more diff for the reviewer, more imports to remember, and more surface area for the next regression. If a third call site appears later, that is the right time to extract.

If a reviewer pushes back on the duplication, the helper extraction is a 5-minute follow-up story.

### Why not just `.catch()` the existing `Linking.openURL` call?

That kills the unhandled-rejection log line, but it does not fix the underlying problem: `Linking.openURL` to an `https://` URL in Expo Go on iOS is the unreliable path. `WebBrowser.openBrowserAsync` is the supported, robust path for arbitrary web URLs in Expo apps, and the codebase already uses it in `ExternalLink.tsx` for exactly this reason. Catching the rejection without changing the API would mean the user still sometimes silently sees the link do nothing.

### Why `console.warn` instead of `console.error` on rejection?

The link is a fallback affordance, not the primary action. If `openBrowserAsync` rejects (system sheet dismissed, user backgrounds the app mid-flight), that is user behavior, not a bug. `console.warn` keeps the signal in Metro for debugging without polluting error reporting.
