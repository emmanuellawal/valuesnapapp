# Story 5.5-5: Lock Epic 6 Workstation Acceptance Criteria

Status: done

## Story

As the SM/PM,
I want every Epic 6 story that touches the desktop workstation model to have fully specified acceptance criteria before implementation starts,
so that the 10/45/45 workstation split, responsive breakpoints, and PWA requirements are never interpreted loosely during Epic 6.

## Background

Epic 5 retro Action Item 5 (High priority) flagged that Stories 6-1 and 6-10 referenced the 10/45/45 workstation model but had no written ACs. The professor's feedback was triggered by vague desktop output in Epic 5. Three stories in Epic 6 need fully locked criteria before any code touches them:

| Story | Title | Gap |
|---|---|---|
| 6-1 | Implement Tab Navigation | No breakpoint gate, no rail-width constraint |
| 6-10 | Implement Desktop UX Patterns | No split percentages, no CLS target, no static-export gate |
| 6-3 | Configure PWA Manifest | No field list, no color tokens |

The Render backend URL (`https://valuesnapapp.onrender.com`) also needs to be cited in network-dependent Epic 6 stories so they have a real endpoint to validate against.

Story 3-6 already shipped `SwissSidebar` with a fixed 240px desktop width. Epic 6 should refine and reuse that existing component under the 10/45/45 workstation model, not create a parallel desktop navigation rail.

**This story produces no code changes** — the sole output is `docs/sprint-artifacts/epic-6-plan.md`.

## Acceptance Criteria

1. `docs/sprint-artifacts/epic-6-plan.md` exists, is not a placeholder, and follows the existing epic-plan structure used by `docs/sprint-artifacts/epic-5.5-plan.md`: intro plus story-by-story sections with `Origin`, `Category`, `Estimate`, `Problem`, `What's Needed`, `Acceptance Criteria`, and `Files to touch`
2. The plan's Story 6-1 section contains ACs covering all four of: mobile bottom-tab layout, desktop rail layout that reuses `SwissSidebar`, breakpoint gate referencing `BREAKPOINTS.desktop` (no magic numbers), and maximum rail width constraint
3. The plan's Story 6-10 section contains ACs covering all six of: 10/45/45 pane split, flex/grid (no hard-coded px), no top header bar on `/appraisal` at desktop breakpoint, `expo export --platform web` clean exit, font preload in exported `index.html`, and CLS ≤ 0.1
4. The plan's Story 6-3 section contains ACs listing all six required PWA manifest fields: `theme_color`, `background_color`, `display`, `name`, `short_name`, and icons at 192×192 and 512×512
5. Network-dependent Epic 6 stories 6-6, 6-7, 6-8, and 6-12 cite `https://valuesnapapp.onrender.com` as the validation endpoint
6. No new magic breakpoint numbers are introduced — all desktop gates reference `BREAKPOINTS.desktop` imported from `constants/breakpoints.ts`
7. Story includes a `## Code Review` section before being marked `done`

### This is documentation-only

### Tailwind breakpoint verification

`apps/mobile/tailwind.config.js` has no local `screens` key, but the resolved Tailwind config still includes default screens through Tailwind/NativeWind:

```json
{
  "sm": "640px",
  "md": "768px",
  "lg": "1024px",
  "xl": "1280px",
  "2xl": "1536px"
}
```

Verified with:

```bash
node - <<'NODE'
const resolveConfig = require('tailwindcss/resolveConfig');
const config = require('./tailwind.config.js');
console.log(resolveConfig(config).theme.screens);
NODE
```

So the earlier assumption that `lg:` is unavailable was wrong. Story 6-1 may use `lg:` responsive classes where appropriate. Runtime layout decisions that depend on React Native dimensions should still use `useWindowDimensions()` + `BREAKPOINTS.desktop`, consistent with Story 3-6.

### Breakpoints constant

`apps/mobile/constants/breakpoints.ts` exports:

```ts
export const BREAKPOINTS = {
  tablet: 600,
  desktop: 1024,
  largeDesktop: 1440,
} as const;
```

The epic plan's earlier notes said `BREAKPOINT_LG = 1024` — that alias does not exist in the file. The correct import is `BREAKPOINTS.desktop`. Story ACs must use this name so there is no confusion.

### Existing sidebar component

`apps/mobile/components/organisms/swiss-sidebar.tsx` already exists from Story 3-6 and is wired into `apps/mobile/app/(tabs)/_layout.tsx`. Epic 6 must refine/reuse this component for the workstation rail. Do not create a second sidebar/rail abstraction unless Story 6-1 explicitly proves the current component cannot support the 10/45/45 model.

### UX spec alignment

The design in `docs/ux-design-specification.md` confirms:
- Mobile: three-tab bottom bar (Camera, History, Settings)
- Desktop: "compact left workstation rail" with 1px dividers
- Ratio: 10/45/45 (navigation / image / data)
- Sidebar note: "visually restrained so content owns the width"
- The spec makes no mention of a `theme_color` or manifest — those details live only in the epic plan; add them there.

### Render URL (already done)

`docs/deployment/README.md` documents `https://valuesnapapp.onrender.com` with health-check and CORS validation instructions. Task D is mostly cross-referencing that URL in the epic plan for network-dependent stories.

### Findings

- HIGH-1 — Story 6-3 did not call out that current `apps/mobile/app.json` uses top-level `"name": "mobile"`, creating a real risk of conflicting PWA/app names. Fixed by requiring `expo.name` to change to `"ValueSnap"` and by documenting Expo camelCase-to-manifest-key mapping.
- HIGH-2 — Story 6-1 banned the old fixed 240px rail width but did not explain that `SwissSidebar` currently hardcodes `style={{ width: 240, flex: 1 }}`. Fixed by adding explicit guidance to replace that fixed width with a responsive capped/minimum rail width.
- HIGH-3 — Story 6-7 risked duplicating the already-shipped `fetchWithRetry` helper from Story 5.5-7. Fixed by requiring reuse/refinement of existing `fetchWithRetry` and no duplicate retry helper.
- MEDIUM-1 — Story 6-3 implied 192x192/512x512 PWA icons already existed. Fixed by requiring creation of those assets under `apps/mobile/assets/images/`.
- MEDIUM-2 — Story 6-3 mixed web manifest keys (`theme_color`, `background_color`) with Expo config shape. Fixed by documenting `expo.web.themeColor` / `expo.web.backgroundColor` as the source config fields.
- MEDIUM-3 — Story 6-10 treated no-header behavior as implementation even though `_layout.tsx` already sets `headerShown: false`. Fixed by changing it to a verification gate.
- MEDIUM-4 — Stories 6-6 and 6-7 both touched `lib/api.ts` without a sequencing note. Fixed by adding 6-7 dependency on 6-6 error mapping and preserving that mapping in retry work.

### Review Result

All HIGH and MEDIUM findings fixed. Story status moved to `done`.
