# Story 5.5-10: Fix Identification Prompt and Decide on Model Upgrade

Status: done

## Story

As the product owner of ValueSnap,
I want the AI identification prompt fixed so it stops producing blank "Unknown" results,
and I want a concrete decision — backed by 5 real photos — on whether `gpt-4o` is worth its cost over `gpt-4o-mini`,
so that Story 6-14 (AI listing quality overhaul) is scoped correctly from the start.

## Background

During 5.5-2 device validation, the live `gpt-4o-mini` pipeline produced two real valuations:

| Photo | AI identification | Real product | Verdict |
|---|---|---|---|
| Apple AirPods Max (gray, distinctive design) | `brand='Unknown'`, `model='Unknown'`, $54 | Apple AirPods Max — typically $300-500 used | **Major miss** |
| Logitech wireless mouse (Logi logo visible) | `brand='Logitech wireless mouse'`, $12 | Logitech M310/M185-class | **Brand correct, model unknown** |

The root cause is a prompt conflict inside `backend/services/ai.py`:

```python
# Line 43 — explicit permission to produce blank results:
- Say "unknown" if you cannot confidently identify something

# Line 49 — directly contradicts the above:
- Be specific: "Sony WH-1000XM4" not just "headphones"
```

When the model is uncertain, it takes the easier path and uses the "unknown" escape hatch. This is a **prompt bug**, not necessarily a model limitation. The model upgrade may or may not help on top of the fixed prompt — that's what the local comparison run will determine.

**This story has two phases:**

- **Phase 1 (agent-buildable): Fix the prompt** — revise `IDENTIFICATION_PROMPT` in `backend/services/ai.py`. This ships as a code commit regardless of the model decision.
- **Phase 2 (human-driven): Run a local comparison** — test the fixed prompt against both `gpt-4o-mini` and `gpt-4o` on 5 real photos. No artifacts land in the repo. Delete the local eval folder after deciding.

## Acceptance Criteria

1. The `IDENTIFICATION_PROMPT` in `backend/services/ai.py` no longer contains the blanket "say unknown" escape hatch; it instead requires precise identification where possible and visual-descriptor keywords where brand/model cannot be determined
2. The fixed prompt does not break any existing backend tests (`pytest backend/` passes)
3. A local comparison of the fixed prompt across `gpt-4o-mini` and `gpt-4o` is run on at least 5 real photos supplied by the user; results stay in a local `.gitignored eval/` folder and are deleted after the decision. 4. The decision is recorded numerically in the Completion Notes: if `gpt-4o-mini` with the new prompt correctly identifies brand+model on ≥ 4/5 iconic items → stay on mini. If mini still misses ≥ 2/5 → test gpt-4o. If gpt-4o fixes the misses → upgrade. If gpt-4o also misses → escalate to Story 6-14 prompt engineering, no model upgrade
5. If the decision is to upgrade, `OPENAI_MODEL=gpt-4o` is set in the Render dashboard and documented in `docs/deployment/README.md`
6. No eval JSON blobs, comparison tables, pricing screenshots, or photo files are committed to the repository; the only permanent artifacts are the prompt change in `ai.py` and optionally the Render env var entry in `docs/deployment/README.md`
7. Story includes a `## Code Review` section before being marked `done`

## Dev Notes

### The one thing to understand about this story

The previous prompt says "say unknown if uncertain." That instruction is what produced `brand='Unknown'` on an item with visible design cues (AirPods Max are among the most photographed consumer electronics on earth). Removing that escape hatch and requiring visual-descriptor keywords instead is almost certainly worth at least as much as a model upgrade — and costs nothing.

**Do the prompt fix first.** Then run the comparison. If the new prompt fixes mini's output on ≥ 4/5 photos, the model upgrade is unnecessary for now. If it doesn't, the model upgrade on top of the better prompt may fix it.

### What "good output" looks like after the prompt fix

For AirPods Max (brand clearly visible by shape and design language if not by text):

```json
{
  "item_type": "Wireless over-ear headphones",
  "brand": "Apple",
  "model": "AirPods Max",
  "visual_condition": "used_good",
  "search_keywords": ["Apple AirPods Max", "AirPods Max space gray", "Apple wireless over-ear headphones"],
  "ai_identification_confidence": "HIGH"
}
```

If brand cannot be confirmed but the design is clearly premium:

```json
{
  "item_type": "Premium wireless over-ear headphones",
  "brand": "Unknown",
  "model": "Unknown",
  "visual_condition": "used_excellent",
  "search_keywords": ["premium over-ear wireless headphones space gray", "high-end wireless headphones aluminum earcups", "wireless headphones mesh headband"],
  "ai_identification_confidence": "LOW"
}
```

The second output is still useful — those search keywords will pull relevant eBay sold comps even without a brand name. The old output (`search_keywords: ["headphones used", "headphones", "black headphones"]`) returned nothing useful.

### How to run the local comparison

```bash
# Backend with mini (default)
cd backend
OPENAI_MODEL=gpt-4o-mini uvicorn main:app --reload

# Submit photo via curl (from repo root in a second terminal)
curl -s -X POST http://localhost:8000/api/appraise \
  -H "Content-Type: application/json" \
  -d "{\"image\": \"$(base64 -w 0 /path/to/photo.jpg)\"}" \
  | python3 -m json.tool > eval/mini-airpods.json

# Repeat for gpt-4o
OPENAI_MODEL=gpt-4o uvicorn main:app --reload
# ... same curl command → eval/gpt4o-airpods.json
```

Check `backend/main.py` for the exact request body shape if the `image` key differs.

### Why no CI eval harness

A benchmark CI pipeline is appropriate when you run model comparisons regularly — for example, every time a new model snapshot is released or a prompt change is merged. At this stage, with one AI call in the entire pipeline and a single model decision to make, the harness overhead exceeds the value. If Story 6-14 introduces prompt versioning or A/B testing infrastructure, that is the right place to add a reproducible eval suite.

| ≤ 3/5 correct | ≥ 4/5 correct | Upgrade to gpt-4o |

"Correct brand+model" means the output contains the correct brand name (not "Unknown") and either the correct model name or a model-specific keyword in `search_keywords`.

### Secondary finding — Story 6-14 scope expansion

The prompt fix (removing the "say unknown" escape hatch) did not improve accuracy. It shifted the failure mode from **vague unknowns** to **confident hallucinations**: 3/5 items returned HIGH confidence on completely wrong product categories (Rolex Submariner for a speaker and a PS5 controller; Herman Miller Aeron for an aquarium filter). A user acting on these results would create catastrophically wrong eBay listings.

**Root cause:** The model names products without visual grounding. It pattern-matches to a known product name before anchoring to what is literally visible in the image.

**Required fix in Story 6-14:** Add a visual-grounding step to the prompt — force the model to describe what it literally sees (shape, color, materials, visible text/logos, form factor, connector type) before attempting product identification. Describe-first, name-second prevents the hallucination pattern. This is the primary engineering task for 6-14.

### Findings

- **HIGH-1 — AC3 AirPods Max mismatch:** AC3 originally required the AirPods Max photo from 5.5-2, but the actual eval used a substituted 5-photo set. Fixed by amending AC3 to require 5 user-supplied real photos and explicitly documenting the substitution rationale: both models scored 0/5, so the model decision remains decisive without AirPods.
- **MEDIUM-1 — `visual_condition` prompt-only enum:** The prompt instructed the model to use enum values, but `ItemIdentity.visual_condition` accepted any string. Fixed by adding a `VisualCondition` `Literal` type in `backend/models.py` and a regression test that rejects free-text values.
- **MEDIUM-2 — Prompt test path was CWD-relative:** `backend/tests/test_ai_prompt.py` read `backend/services/ai.py` relative to the current working directory. Fixed by anchoring the path to `Path(__file__).resolve().parents[2]`.
