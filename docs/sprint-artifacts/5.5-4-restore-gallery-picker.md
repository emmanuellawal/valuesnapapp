# Story 5.5-4: Restore Gallery Picker to Main Mobile Flow

Status: review

## Story

As a ValueSnap user with camera permission already granted,
I want to select a photo from my device's camera roll instead of taking a new photo,
so that I can appraise items I photographed earlier without needing to re-photograph them.

## Acceptance Criteria

1. On iOS/Android with camera permission granted, a "Choose from library" secondary action is visible and tappable in the `idle` state of the camera capture area
2. On iOS/Android with camera permission granted, a "Choose from library" secondary action is visible and tappable in the `ready` state of the camera capture area
3. Selecting a photo from the library routes it through the same `onPhotoCapture` callback as the camera capture path — no duplicate `launchImageLibraryAsync` logic exists; `handleFileUpload` remains the single call site
4. The library button meets accessibility requirements: `accessibilityLabel` is set and touch target is ≥ 48px
5. On web, the "Choose from library" button opens the browser file picker (no separate implementation needed — `launchImageLibraryAsync` handles web automatically)
6. Existing `denied` state "Upload Photo" button continues to work through the shared `handleFileUpload` path (same successful behavior, now including the Android media-library permission guard)
7. Android only: `requestMediaLibraryPermissionsAsync` is called before `launchImageLibraryAsync` to prevent a silent crash on devices that require explicit permission; iOS/web do not receive an extra preflight prompt
8. New unit tests in `__tests__/camera-capture.test.tsx` cover: library button visible in `ready` state, pressing it calls `onPhotoCapture` with the selected photo URI
9. Existing tests in the suite still pass (no regressions)
10. Story includes a `## Code Review` section before being marked `done`

## Dev Notes

### Problem in a sentence

`handleFileUpload` works perfectly — it calls `launchImageLibraryAsync`, handles cancel, and routes photos through `onPhotoCapture`. It is only ever reachable via the `denied` state's "Upload Photo" button. Users who grant camera permission never see this path. Fix: expose the button in `idle` and `ready`.

### Do NOT create a new launch handler

The epic plan is explicit: "Re-use `handleFileUpload` — do not duplicate logic." Both new buttons call `handleFileUpload` directly. The `denied` state's existing "Upload Photo" button continues to call it. Three callers, one function.

### handleFileUpload routes directly to `captured` — not through `preview`

Currently `handleFileUpload` sets `setCameraState('captured')` and calls `onPhotoCapture(photo)` immediately, bypassing the preview/retake flow. This is **acceptable and intentional** for library picks: the user already previewed the photo in the system picker. Do NOT change this to go through `preview` — it would allow a "Retake" button that relaunches the camera (wrong UX for a library pick). The divergent state paths are by design.

### expo-image-picker v17 API — already correct in existing code

The existing `handleFileUpload` already uses the correct v17 syntax:
```ts
await ImagePicker.launchImageLibraryAsync({
  mediaTypes: ['images'],   // array, not MediaTypeOptions.Images enum
  quality: CAMERA_QUALITY,
  allowsEditing: false,
});
```
Do **not** change this. The old `MediaTypeOptions.Images` enum was deprecated in v15 and removed in v17.

### `requestMediaLibraryPermissionsAsync` placement

Add it as an Android-only guard inside `handleFileUpload`, before `launchImageLibraryAsync`:
```ts
const handleFileUpload = useCallback(async () => {
  if (Platform.OS === 'android') {
    const { status } = await ImagePicker.requestMediaLibraryPermissionsAsync();
    if (status !== 'granted') {
      setErrorMessage('Library access is required to choose a photo.');
      return;
    }
  }
  try {
    const result = await ImagePicker.launchImageLibraryAsync({ ... });
    ...
  }
}, [onPhotoCapture]);
```
iOS and web should skip this preflight and rely on `launchImageLibraryAsync` to avoid duplicate permission prompts.

### Swiss design for the secondary button

The primary action in `idle` and `ready` is the large tap target. The library button is deliberately secondary:
```tsx
<SwissPressable
  onPress={handleFileUpload}
  accessibilityLabel="Choose a photo from your library"
  accessibilityHint="Opens your photo library"
  className="py-4 items-center"
  testID="camera-pick-library-idle"
>
  <Text variant="caption" className="text-ink-muted">
    Choose from library
  </Text>
</SwissPressable>
```
No icon. No border. Lowercase-first text is acceptable here — `variant="caption"` implies secondary/subdued. Keep it flush with the layout grid below the camera prompt text.

### Test file strategy

Do not mock `@/components/primitives` unless absolutely necessary. `SwissPressable` composes native `Pressable`, so tests can target `testID` and `onPress` directly on the real component tree.

If mocking is required for a specific flaky path, use `apps/mobile/test-utils/mock-organisms.tsx` only as a naming/style reference; it mocks organisms, not primitives.

### Advancing `CameraCapture` to `ready` state in tests

`CameraCapture` starts in `idle`. To reach `ready`, you need to simulate the `handleActivateCamera` press:
```ts
const activateButton = renderer.root.findByProps({ testID: 'camera-capture-idle' });
// or find the SwissPressable inside the idle box:
await act(async () => {
  activateButton.findByType(Pressable).props.onPress();
  await Promise.resolve();
});
// Now cameraState === 'requesting' → 'ready' (mocked useCameraPermissions resolves immediately)
```
Alternatively, mock `useCameraPermissions` to return `[{ granted: true }, jest.fn()]` and set the initial state to bypass the activation tap — but since `CameraCapture` has no external `initialState` prop, starting from `idle` and pressing the activate button is the canonical path.

`expo-image-picker` is already in `package.json` (`^17.0.10`). `requestMediaLibraryPermissionsAsync` is part of the same package. No `npm install` required.
